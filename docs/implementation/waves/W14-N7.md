## 0. What the round was handed

`run_evals.py`'s report-only answer layer was not reproducible. Five
consecutive runs earlier the same day gave four different distributions
(ABSTAIN 13–14, COMPLETE 11–14, QUALIFIED 4–6, false abstentions 0 or 1 —
always `fx-amend-002`), while every hard gate, every retrieval metric and the
lane distribution were identical every time. `W14-M-SRV` had already proved the
cause is INGEST-side: the answer driver run repeatedly against ONE ingested
database (`--skip-ingest`) is byte-identical, while re-ingesting the same
corpus changes the outcome.

Three ingest-id fixes had already landed the same day, before this round:

1. `control-plane/src/store/chunkStore.ts` — the citator lane's two queries
   ended their `ORDER BY` on `legal.document_relations.id`; they now use
   `stableRelationTieBreak`.
2. `control-plane/src/store/chunkStore.ts` — the pinned-legislation window
   function partitioned by `legislation_no` and ordered by `(c.ordinal, c.id)`;
   it now orders by `(c.ordinal, d.source, d.external_id, c.id)`.
3. `ingestion/relations.py` — the candidate-law query had no `ORDER BY` at all;
   it now groups and orders by `(d.source, d.external_id, d.id)`.

**All three are real defects and none of them closed the variance.** They stand.

## 2. Step 2 — instrument the gold row that flips (`fx-amend-002`)

`fx-amend-002` is *"7999 sayılı Kanun ile 6098 sayılı Türk Borçlar Kanununda
hangi değişiklik yapılmıştır?"*, `as_of` 2026-03-01, `acceptable_abstention:
false`.

A trace driver was built against the SAME code the product runs — real
`AnswerPipeline`, real `createStoreRetrievalPort` / `createStoreTextPort` /
`createStoreVersionFactsPort`, `DEFAULT_ANSWER_LIMITS` — with the retrieval port
wrapped so that **every retrieval call's ordered candidate list** was captured
and every chunk id, relation id and via-id was rewritten to its corpus identity
(`<external_id>@<version_label>#<structural_path>`) before comparison. It then
dumped the evidence pack, the claims, the coverage decision, the verdict and
the pipeline's own trace.

Two ingests, one question. The first divergence:

* **Every retrieval lane returned the SAME ordered list in both ingests.** Five
  retrieval calls (the primary query plus four contrary lanes), 14 / 7 / 10 / …
  hits each, identical rank by rank, identical lane provenance, identical
  scores. The only per-hit difference was the `citedByChunkId` label carried by
  citation-expansion hits — an id, not an order.
* **`contraryCoverage.observed` differed.** Which passages were set aside as
  `EVIDENCE_CAP_APPLIED` and which as `QUESTION_NOT_COVERED` was a different
  partition of the same candidate set:

  | | dropped by the cap in ingest A | dropped by the cap in ingest B |
  |---|---|---|
  | differing entries | `kanun-7999@v1-20260115#madde-3/fikra-1`, `kanun-6098@v1-20120701#madde-1/fikra-2`, `kanun-6098@v1-20120701#madde-12/fikra-1` | `kanun-7999@v1-20260115#madde-4/fikra-1`, `kanun-6098@v1-20120701#madde-51/fikra-1`, `kanun-6098@v1-20120701#madde-49/fikra-1` |

Walking backwards from that divergence reaches exactly one line.

### The cause

`control-plane/src/pipeline/answerPipeline.ts`, the `rank` stage:

```ts
rows.sort((a, b) => {
  if (a.hit.pinned !== b.hit.pinned) return a.hit.pinned ? -1 : 1;
  if (b.hit.fusedScore !== a.hit.fusedScore) return b.hit.fusedScore - a.hit.fusedScore;
  return a.hit.chunkId < b.hit.chunkId ? -1 : a.hit.chunkId > b.hit.chunkId ? 1 : 0;  // <- uuid
});
```

`hit.chunkId` is `gen_random_uuid()`, minted at ingest.

Why it bit so hard: **every passage that arrives on the citation, citator
(relation) or contrary lane carries `fusedScore: 0`** — those lanes append or
interleave, they do not participate in the RRF fusion. On a question like
`fx-amend-002`, which is answered largely through amendment edges and citation
expansion, the tie group is most of the candidate list, so the uuid alone
ordered it. `coverageAwareCap(eligible, 8, …)` then kept a different eight
after every re-ingest, and the coverage gate, the drafter, the verifier and the
finalization policy all read that different eight.

Retrieval was never the variable. The CAP was.

### The audit that came with it

Every `ORDER BY` in `control-plane/src/**` and every JavaScript sort in
`store/`, `retrieval/`, `answer/` and `pipeline/` was read for an
ingest-unstable key (a uuid, insertion order, an unordered aggregate, Set/Map
iteration seeded by a uuid, a LIMIT without a total order). After this fix the
only `chunkId`-based comparison left in `control-plane/src` is inside
`stablePassageKey` itself, as the last-resort term; `hybrid.ts`'s fused
ordering and `chunkStore.ts`'s lanes already end on corpus identity, and
`coverageAwareCap` is index-based over an already-ordered list.

## 3. The fix

`control-plane/src/pipeline/answerPipeline.ts`:

```ts
return compareStable(stablePassageKey(a.hit), stablePassageKey(b.hit));
```

with

```ts
function stablePassageKey(hit: RankedHit): string {
  const p = hit.provenance;
  return [p.source, p.externalId, String(p.ordinal).padStart(9, "0"), hit.chunkId]
    .join(PASSAGE_KEY_SEP);   // "\0"
}
```

`(source, external_id, ordinal)` is the corpus identity the ingest does not
mint — the SAME key `chunkStore.stableTieBreak` and `hybrid.stableKey` already
use, so the three layers now break ties the same way. `chunkId` stays last so
the ordering is total even if two passages ever tie on all three. The separator
is `"\0"` written as an escape, never as a raw NUL byte
(`tests/test_repo_hygiene.py`).

**This is a behaviour change, and it is the intended one.** It does not make an
answer "better"; it makes the top-8 the same one every time, chosen by the
corpus rather than by a random number. Nothing was pinned to an ingest, no lane
was disabled, no threshold moved, and the gold set was not touched.

## 5. Regression test, and its non-vacuity

`control-plane/tests/pipeline/rankDeterminism.test.ts` (NEW, 2 tests). One
corpus of twelve passages, two "ingests": identical text, identical order out
of retrieval, identical `fusedScore: 0` — the only difference is that the
second mints chunk ids sorting the OPPOSITE way. The passages are deliberately
identical in wording apart from a marker carrying no question word, so
`coverageAwareCap` performs no swaps and the kept set is decided by the
tie-break alone.

* Test 1: the two ingests keep the SAME eight passages and set aside the same
  four.
* Test 2: both keep the first eight in CORPUS order.

**Non-vacuity, proven by reintroducing the defect once.** The uuid tie-break was
put back, the suite run, and BOTH tests failed:

```
AssertionError: direction=desc: expected [ 'kanun-n7-12', 'kanun-n7-11', …(6) ]
                                to deeply equal [ 'kanun-n7-01', 'kanun-n7-02', …(6) ]
```

— the descending ingest kept documents 12..05 while the ascending one kept
01..08, which is precisely the failure mode `fx-amend-002` exhibited on the real
corpus. The fix was then restored and both tests pass.

## 6. What is still ingest-dependent, and why it was left

**One thing, and it is a LABEL, not a number.**
`answer/evidencePack.ts::deterministicEvidenceId` derives an evidence id as
`ev-` + `sha256("<documentVersionId>|<startChar>|<endChar>")[:16]`, and
`documentVersionId` is an ingest-minted uuid. So the `ev-<hex>` strings inside
the `reasons` text of three gold rows — `fx-fact-001`, `fx-contrary-001`,
`fx-contrary-002`, all in `CONFLICTING_AUTHORITIES:<claimId>:<evidenceIds>` —
differ between ingests. That is the ONE difference left between two report JSONs
(§4.2).

It moves nothing: no count, no rate, no status, no gate, no ORDER. §4.1
compared those same `reasons` lists with every `ev-<hex>` rewritten to the unit
it names, across five ingests, and they were identical — so the semantic
content and the order of those reason lines are stable; only the spelling of the
id is not.

**It was deliberately not changed, and the reason is product behaviour, not
effort.** `evidenceId` is a PERSISTED identifier: it is written into stored
answer records and draft versions, it is what a draft's claims cite, it appears
in exported evidence bundles and in the `EK — DOĞRULAMA BİLGİLERİ` section, and
the quote-integrity bond is expressed in terms of it. Re-deriving it from corpus
identity would change every id in every record already written. That is a
migration and a decision of its own, not a determinism fix, and N-7 does not
need it.

## 8. What a later round should know

1. **Any new ordering, cap or LIMIT in `store/`, `retrieval/`, `answer/` or
   `pipeline/` must end on `(source, external_id, ordinal)`, never on a uuid.**
   Three layers now agree on that key (`stableTieBreak`, `stableKey`,
   `stablePassageKey`); a fourth that does not will reopen N-7 in a new place.
2. **The band stays.** It is now width zero, and that zero is the proof —
   which only exists because the harness measures more than one ingest. Never
   read a single run as the measurement, and remember that TWO agreeing runs
   are not proof either: the round that found this had two runs agree digit for
   digit before the next four disagreed.
3. **`fx-amend-002` is now a STABLE false abstention** (1 in all six runs), not
   an intermittent one. It is report-only and it is a real, reproducible
   product question: the corpus does answer it. That is now a debuggable
   finding rather than noise — which is most of what closing N-7 bought.
4. **Phase F's reading of `fx-amend-003`** (QUALIFIED → COMPLETE, three lost
   `CONFLICTING_AUTHORITIES`) was taken while this layer moved. It can now be
   re-measured honestly. It was not re-measured here.
